# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff matches plan scope | The diff's changed files and hunks, read against the plan's (or plan context's) In-scope/Not-in-scope statement and any Deviations note | Pass if every changed file and every hunk falls inside the plan's stated in-scope area, or is named in a deviation note written into the plan before/alongside the PR. Fail if the diff touches a file or behavior the plan scopes out or never mentions, and no deviation note accounts for it — regardless of whether the extra change looks adjacent or beneficial. Unclear if the package has no plan scope statement to compare against | required |
| Description matches the diff | The PR description's claims about what the change does, read against the diff's actual contents | Pass if every substantive claim the description makes about the change (the mechanism fixed, a feature/file added, a behavior updated) is something the diff actually contains in substance, and the description names anything the plan called for that the diff does NOT deliver (an honest disclosed shortfall). Judge a claim by whether the diff delivers its substance, not by a literal count — e.g., a description saying "tests added for cases A, B, and C" passes when one test function's assertions cover A, B, and C, even if they aren't three separate test functions. Fail if the description claims a mechanism, file, or behavior change the diff does not contain at all, or claims total fidelity ("exactly as planned", "no changes beyond it") while the diff contains an unmentioned extra hunk that does something the plan didn't scope in. Unclear if the description is too vague to compare against the diff at all (e.g., no description of what changed) | required |
| Test evidence is decisive | The PR's test-evidence section (or `test_evidence.md`), read against the plan's test plan and the original repro evidence's steps | Pass if the evidence names the specific behavior from the plan's test plan that exercises the actual fix, and shows it before (bug present) and after (bug gone) in observable terms (an error trace, a returned value, a diffed/byte-identical output, or an equivalent assertion in an added automated test — not prose alone), AND accounts for every control or secondary step the plan's test plan named, each with a specific, concrete statement of its result (e.g., "the no-ampersand control unchanged", "the all-comments control unchanged") — a control does not need its own separately pasted transcript to pass, a named, specific claim about its outcome is sufficient; only a vague or absent accounting of a named control fails this. Also reports the repo's own required checks with their real outcome, even a failing or inapplicable one, as long as it's reported honestly with a reason. Fail if the evidence is a bare assertion ("tested locally, works now", "cargo test passes") with no named before/after tied to the plan's specific repro step, exercises only an already-working/control path while leaving the plan's actual repro step unrun, silently drops a control or secondary test-plan step the plan named with no accounting at all, or omits the repo's own checks entirely. Unclear if no test-evidence section exists at all | required |
| Diff is reviewable | The unified diff and the commit list | Pass if every hunk in the diff is part of the change the plan describes, with no debug prints or logging left in, no commented-out code, no dead function or block kept around, and no formatting-only or unrelated-rename churn riding along; commit messages describe the change rather than reading as process notes ("wip", "fmt", "cleanup"). Fail if any debris of this kind is present anywhere in the diff, however small, or however good the actual fix is | required |
| Repo standards met | The repo's stated PR-template sections and contribution/AI-disclosure policy (the repo-facts block, or Path Review's `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md` in live mode), read against the PR's description and checklist | Pass if every section the template requires is filled with real, PR-specific content (not a restated heading or the template's own placeholder comment), `Closes #<issue>` names the correct issue, only genuinely-true checklist boxes are ticked (a seeded-bug fix ticks the xfail-removal box only if the diff actually removes the marker and any matching `pyproject.toml` suppression), and an AI-use disclosure is present wherever the repo's stated policy (or, in live mode, the course's standing disclosure requirement) requires one, written specifically to this change rather than as boilerplate. Fail if any required section is left as a placeholder or omitted, `Closes #` is missing or wrong, a checklist box is ticked without the diff supporting it, or a required disclosure is absent. Unclear if the package states no template or policy at all to check against (pass by default in that case, per the verdict rule below) | required |
| Honest about unknowns | The plan's/package's Risks or Deviations section, read against how confidently the description is written | Pass if a genuine shortfall, deferred piece, or untraced edge case is named plainly as such, in the place meant for it (plan.md's Risks/Deviations, or the description's own disclosure language), rather than omitted or apologized around. Fail if the description reads as fully confident while the plan or package itself records an open risk or an intentionally deferred piece that the description never mentions. Unclear only if there is truly no way to tell whether an unknown exists | preferred |

## Verdict rule

Accept if every `required` check grades `pass`. Reject if any
`required` check grades `fail`. `unclear` on a required check is
treated as `fail`, with one named exception: "Repo standards met"
grades `pass`, not `fail`, when the package states no template and no
policy to check against at all (nothing to comply with is not a
compliance failure) — but in live mode this exception never applies,
because Path Review's template and `docs/CONTRIBUTING.md` are always
present to check against. `unclear` on every other required check
(diff-vs-plan, description-vs-diff, test evidence, diff reviewability)
always means reject: a PR whose fidelity, evidence, or cleanliness I
cannot verify from the package is not ready to submit. The `preferred`
check (Honest about unknowns) is reported but never changes the
verdict; a disclosed shortfall that passes the other five required
checks stays `accept`, because "less than everything, disclosed" is not
the same failure as "less than everything, hidden" (the latter fails
under Diff matches plan scope or Description matches the diff instead).
